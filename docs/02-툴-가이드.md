## 1. 설계 원칙 두 가지

이 도구의 거의 모든 성질이 아래 두 결정에서 나온다.

### Core(순수 C#) / Unity(뷰) 분리

게임 로직에 `UnityEngine` 참조가 **하나도 없다.**

- 유니티를 켜지 않고 `dotnet` 만으로 컴파일·실행·검증된다
- 그래서 AI 가 "코드 수정 → 컴파일 → 에러 읽기 → 재수정" 루프를 혼자 돈다
- 밸런스 시뮬레이터가 같은 코드를 수만 번 돌릴 수 있다 (유니티 위였다면 불가능)

### 화면을 런타임에 코드로 생성

프리팹을 만들거나 인스펙터에 드래그로 참조를 꽂는 작업이 **없다.**

- 씬에 `GameRunner` 컴포넌트 하나만 있으면 게임이 성립한다
- 항목이 늘거나 줄어도 화면이 자동으로 따라온다
- 사람이 유니티에서 할 일이 Play 버튼 하나로 줄어든다

기본 화면 모드는 **2D**(`view: "sprite2d"`)다. 판과 경로는 월드에 `SpriteRenderer` 로 그리고,
상단 정보와 하단 버튼만 UI 캔버스로 올린다 — 실제 2D 모바일 게임의 구성이다.
방치형처럼 원래 UI 게임인 경우에만 `view: "ui"` 로 두면 전부 캔버스로 그린다.

## 2. 지원 장르 6종

모바일 다운로드 규모와 자동화 적합도를 함께 보고 골랐다.

| genre | 장르 | 대표작 | Core 가 다루는 것 |
|---|---|---|---|
| `match3` | 매치3 퍼즐 | 캔디크러시, 로얄매치 | 실제 판, 매치·낙하·연쇄, 수 제한, 스테이지 목표 |
| `merge` | 머지 | 머지드래곤, 가십하버 | 합성 판, 에너지, 아이템 생산 |
| `idle` | 방치형/타이쿤 | 포지마스터, 어드벤처캐피탈리스트 | 생산 시설, 업그레이드, 오프라인 보상 |
| `survivor` | 서바이버 | Survivor.io, 뱀파이어서바이버 | 자동 공격, 몰림 압력, 레벨업 강화 |
| `towerdefense` | 타워디펜스 | 타워워, 랜덤디펜스 | 웨이브, 타워 배치·강화, 경로 |
| `autobattler` | 오토배틀러/방치형 RPG | 탑워, AFK아레나 | 팀 편성, 자동 전투, 스테이지 진행 |

### 추상화 수준이 장르마다 다른 이유

- **매치3만 실제 판을 굴린다.** 이 장르는 난이도가 판 배치에서 나오기 때문에 추상화하면 의미가 없다.
- **타워디펜스는 경로를 1차원 거리로 다룬다.** 밸런스 판정에는 그것으로 충분하고, 시뮬이 수만 배 빨라진다. 화면에 그릴 때만 Unity 가 그 거리를 실제 경로 위 좌표로 옮긴다.
- **서바이버·오토배틀러는 흐름으로 푼다.** 개별 유닛 좌표 대신 "총 DPS vs 총 체력", "적 유입량 vs 처치량" 으로 압축한다. 이 장르들의 밸런스는 사실상 그 비로 결정된다.

## 3. 명령어

실행 파일은 `Tools/GameForge/bin/Debug/net9.0/gameforge.dll`.
아래에서는 `gameforge` 로 줄여 쓴다.

```bash
# 최초 1회
dotnet build Tools/GameForge/GameForge.csproj
```

### scaffold — 기본 기획서 만들기

```bash
gameforge scaffold --genre match3 --name MyPuzzle --display "내 퍼즐"
# -> Specs/mypuzzle.json
```

장르별 기본값이 채워진 기획서가 나온다. 이걸 고쳐서 쓰거나, 문서에서 옮긴 값으로 덮어쓴다.

### schema — 쓸 수 있는 필드 보기

```bash
gameforge schema
```

기획서를 문서에서 스펙으로 옮길 때 참고하는 필드 전체 안내.

### validate — 기획서 점검

```bash
gameforge validate Specs/mypuzzle.json
```

빠진 필드, 없는 id 참조, 말이 안 되는 수치를 잡는다.
`gen` 이 이걸 먼저 돌리므로 **오류가 있으면 생성 자체가 중단된다.**

### gen — 생성

```bash
gameforge gen Specs/mypuzzle.json
```

Core·Unity·Editor 코드와 밸런스 시뮬레이터를 전부 만든다. 항상 덮어쓴다.

### apply — 튜닝 결과 반영

장르마다 축 이름이 다르다.

| genre | 옵션 |
|---|---|
| `idle` | `--cost-growth` `--tier-factor` |
| `towerdefense` | `--hp-growth` `--reward-growth` |
| `merge` | `--energy-regen` `--income-growth` |
| `autobattler` | `--stage-growth` `--reward-growth` |
| `survivor` | `--enemy-hp-growth` `--spawn-growth` |
| `match3` | `--moves` `--target-growth` |

```bash
gameforge apply Specs/mypuzzle.json --moves 30 --target-growth 1.04
gameforge gen Specs/mypuzzle.json
```

### genres — 장르 목록

```bash
gameforge genres
```

## 5. Core / Unity 분리가 왜 중요한가

`Sim/<Name>/<Name>.Sim.csproj` 는 Core 의 `.cs` 를 **사본이 아니라 링크로** 참조한다.

```xml
<Compile Include="../../Assets/Games/<Name>/Core/**/*.cs" />
```

즉 **시뮬레이터가 돌리는 코드와 게임에서 도는 코드가 글자 그대로 같은 파일이다.**
"시뮬에서는 되는데 게임에서는 다르다" 가 구조적으로 불가능하다.

### 결정론

- 전투 수치는 `Fx`(Q16.16 고정소수점)
- 난수는 `DetRandom`(xorshift, 시드 고정)

같은 시드 + 같은 입력이면 언제 어디서 돌려도 결과가 같다.
지금은 싱글 게임에만 쓰지만, 나중에 협동 모드를 붙일 때 "입력만 주고받는" 구조로 확장할 수 있게 미리 깔아둔 것이다.
나중에 개조하려면 전투 코드를 갈아엎어야 한다.

### 큰 수

방치형 재화는 `BigNumber`(가수+지수)로 다룬다. `1.23aa` 같은 표기까지 포함해 오버플로가 없다.

## 6. 밸런스 시뮬레이터

### 기본 실행

```bash
dotnet run --project Sim/<Name>/<Name>.Sim.csproj
```

가상 플레이어가 게임을 대신 플레이한 결과를 보고한다. 장르마다 보는 지표가 다르다.

| genre | 핵심 지표 |
|---|---|
| `idle` | 시설 해금 시각, 1/7일차 진행, 정체 구간 |
| `towerdefense` | 웨이브별 도달률, 주력 타워별 전략 성능 |
| `merge` | 최고 레벨 도달 시각, 에너지 유휴 비율 |
| `autobattler` | 스테이지 진행, 전투 승률, 유닛별 레벨 |
| `survivor` | 평균 생존 시간, 완주율, 무기별 성능 |
| `match3` | 스테이지 도달률, 시도당 클리어율, 벽 위치 |

### 자동 튜닝

```bash
dotnet run --project Sim/<Name>/<Name>.Sim.csproj -- --tune
```

두 축을 격자로 훑어 목표에 가장 가까운 조합을 찾는다.

```
  수 제한 / 목표점수 증가율  1.04      1.06      1.08      1.10
      22수                 13.1단/80%  10.3단/76%   8.7단/72%   8.3단/71%
      26수                 19.4단/86%  13.9단/81%  10.7단/76%   9.0단/73%
      30수                 23.0단/88%  16.6단/84%  13.3단/80%  11.0단/77%

추천 조합: moves = 22, targetGrowth = 1.10
```

### 축이 하나면 안 되는 이유

실제로 겪은 사례다. 방치형에서 `costGrowth` 만 훑었더니 1.04→1.46 전 구간이 3.5분→7분으로 거의 변하지 않았다.
**그 파라미터가 지렛대가 아니었다.** 티어 간 기본가 배율을 두 번째 축으로 넣자 4분 ~ 미도달까지 폭이 벌어졌고,
목표(7일)에 맞는 조합을 찾을 수 있었다.

같은 이유로 **아무도 클리어하지 못하는 구간에서는 클리어율만 봐서는 기울기가 없다.**
평균 도달 웨이브/스테이지를 함께 보여줘야 "어느 방향이 덜 나쁜지" 가 보인다.

### 튜닝으로 못 고치는 것

시뮬이 "어떤 조합에서도 안 된다" 고 말하면 그건 수치 문제가 아니라 **구조 문제**다. 실제로 나온 예:

- 타워디펜스에서 슬롯을 다 채우면 골드가 갈 곳이 없어 후반 화력이 원천 부족 → **타워 강화 시스템 자체가 없었다**
- 보스 웨이브에서 적 전원의 체력이 배가 되고 있었다 → **보스는 한 마리여야 한다**
- 적 체력만 웨이브마다 지수로 오르고 처치 보상은 고정 → **수입이 난이도를 따라갈 수 없다**

셋 다 튜너가 "0%" 를 계속 뱉어서 발견했다.

## 7. 화면은 어떻게 만들어지는가

장르마다 화면을 따로 짜면 6종을 감당할 수 없다. 그래서 중간 표현을 하나 둔다.

```
                              ┌──▶ WorldView  판·경로를 2D 스프라이트로 (월드)
Core 의 GameUi  ──▶  UiModel ─┤
 (장르마다 구현)      (중간 표현) └──▶ Hud        정보·버튼을 UI 로 (캔버스)
```

`GameRunner` 가 매 프레임 `UiModel` 을 한 번 만들고, 두 뷰가 `LateUpdate` 에서 읽기만 한다.
빌드 순서를 확정하기 위한 구조다.

`UiModel` 이 가진 것은 네 가지뿐이다.

| 요소 | 쓰는 장르 |
|---|---|
| `Stats` — 상단 정보 줄 | 전부 |
| `Actions` — 아이콘+제목+부제 버튼 목록 | 전부 |
| `Grid` — 격자 판 | 매치3, 머지 |
| `Track` — 1차원 경로 | 타워디펜스, 서바이버(진행바) |

`Grid` 와 `Track` 은 2D 모드에서 `WorldView` 가, UI 모드에서 `Hud` 가 그린다.
`Stats` 와 `Actions` 는 어느 모드에서든 `Hud` 가 그린다.

**장르를 추가해도 유니티 쪽 코드는 건드리지 않는다.** 해당 장르의 `GameUi` 만 쓰면 된다.

### 입력

2D 모드의 판·경로 터치는 카메라 좌표 변환으로 판정한다(물리 콜라이더를 쓰지 않는다).
입력 API 는 프로젝트 설정에 따라 갈린다.

| Active Input Handling | 동작 |
|---|---|
| `Both` 또는 `Input Manager (Old)` | 정상 |
| `Input System Package (New)` 전용 | **UI 버튼과 화면 터치가 모두 죽는다** |

새 Input System 전용 설정에서는 `StandaloneInputModule` 이 런타임 예외를 던지기 때문이다.
생성된 코드는 두 경우 모두 컴파일되지만, 새 Input System 전용일 때는 경고를 찍고 입력을 받지 않는다.

```
메뉴 > GameForge > <게임> > 프로젝트 설정 점검
메뉴 > GameForge > <게임> > 입력 설정을 Both 로 변경   (에디터 재시작 필요)
```

### 아트

`icon` 을 비워두면 색 플레이스홀더가 코드로 생성된다(팔레트를 황금비로 돌려 인접 항목끼리 색이 안 겹친다).
이미지는 `Assets/Games/<게임>/Resources/Icons|Sprites/` 에 넣고 기획서에는 파일명만 적는다.
자세한 규칙은 [03-리소스-넣는-법.md](03-리소스-넣는-법.md).

## 8. 검증 방법

**유니티를 켜지 않는 것이 기본이다.** 사용자가 에디터를 열어둔 채 작업할 때가 많아
`-batchmode` 는 "another Unity instance is running" 으로 막힌다.

```bash
# 1) 생성기 자체
dotnet build Tools/GameForge/GameForge.csproj

# 2) 게임 로직 + 시뮬레이터 (순수 C#)
dotnet build Sim/<Name>/<Name>.Sim.csproj

# 3) 유니티 레이어 — 유니티 관리 DLL 직접 참조
dotnet build Tools/UnityCheck/UnityCheck.csproj
```

### UnityCheck 가 C# 9 인 이유

**유니티는 C# 9 까지만 지원한다.** 검사 프로젝트를 `LangVersion=latest` 로 뒀다가
파일 범위 네임스페이스(C# 10)를 생성 코드에 넣고도 통과시켜 버린 적이 있다.
유니티에서 `CS8773` 로 8개 파일이 한꺼번에 깨졌다. 그래서 `9.0` 으로 고정해 두었다.

## 9. 장르를 추가하려면

1. `Tools/GameForge/Spec/GameSpec.cs` 에 장르 전용 스펙 클래스 추가
2. `Tools/GameForge/Spec/Presets.cs` 에 기본값 추가
3. `Tools/GameForge/Spec/Validator.cs` 에 점검 규칙 추가
4. `Tools/GameForge/Gen/<장르>Emitter.cs` 작성 — 아래 다섯을 내보낸다
   - `GameData` (밸런스 테이블 + `ApplyTuning`/`ResetTuning`)
   - 시스템 클래스들 (`ISimSystem` 구현)
   - `AutoPlayer` (가상 플레이어)
   - `GameUi` (`IUiProvider` 구현)
   - `GameFactory` (`Create` + `CreateUi`)
5. `Tools/GameForge/Gen/SimEmitter.cs` 에 시뮬레이터 본문 추가
6. **등록 세 곳** — 하나라도 빠지면 깨진다
   - `Program.Generate` 의 switch
   - `SimEmitter.ProgramFor`
   - `EditorEmitter.IconLoop`

공용 런타임(`Fx`, `BigNumber`, `DetRandom`, `SimWorld`, `UiModel`), 유니티 뷰, 에디터 스크립트는 손댈 필요가 없다.

## 10. 알려진 한계

### 아직 안 한 것

- **Play 실행 확인** — 컴파일은 전부 통과했지만 실제로 유니티에서 굴려본 적은 없다
- **Input System 패키지가 깨져 있다** — `com.unity.inputsystem` 1.12.0 이 에디터 6000.3.11f1 과 안 맞아 컴파일 실패 상태다. 입력을 쓰려면 패키지를 업데이트하거나 Active Input Handling 을 `Both` 로 바꿔야 한다
- **배경 이미지와 사운드 재생** — 폴더만 준비돼 있고 코드는 없다
- 세이브/로드
- 오프라인 보상 UI (계산 경로는 있으나 화면이 없다)
- 광고·IAP 훅
- 에셋 자동 임포트/아틀라스

### 프리셋 밸런스

장르별 기본값은 **출발점일 뿐이고 완성된 밸런스가 아니다.** 실측으로 확인된 상태:

| genre | 상태 |
|---|---|
| `survivor` | 완주율 40%, 무기 편차 88~100% — 양호 |
| `match3` | 튜닝 후 평균 23/50 스테이지, 클리어율 88% — 양호 |
| `idle` | 튜닝 후 전 시설 해금 3.6일 — 양호. 다만 중간 3종이 몰려 열리는 구간 압축이 남아 있다 |
| `towerdefense` | 클리어율 60% 정체. 난이도가 아니라 **타워 역할 분화 실패** — 서리탑(지원형)·마법탑이 단독 전략으로는 3웨이브에서 죽는다 |
| `merge` | 최고 레벨 2.2시간 도달(너무 빠름), 에너지 유휴 73% — 판이 꽉 차서 소환을 못 한다 |
| `autobattler` | 스테이지는 진행되나 승률 2% — 재도전 반복 구조. 성장률 조정 필요 |

**실제 기획서가 들어오면 그 수치로 다시 튜닝하므로 프리셋 밸런스 자체는 중요하지 않다.**
위 표는 "시뮬이 문제를 제대로 잡아낸다" 는 증거로 남겨둔다.

### 시뮬레이터의 구조적 한계

- **단일 전략만 시험한다.** 타워디펜스는 "이 타워만 주력으로 쓰면 몇 웨이브까지 가나" 를 재므로, 서리탑처럼 단독으로 쓰라고 만든 게 아닌 지원형 타워가 부당하게 낮게 나온다. **혼합 전략 시뮬**이 필요하다.
- **매치3 가상 플레이어는 한 수 앞만 본다.** 연쇄를 노리는 수를 못 찾으므로 사람보다 약간 못하다. 여기서 클리어되는 난이도면 사람은 여유 있게 깬다 — 안전한 방향의 오차다.
